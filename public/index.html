A SAFER WAY TO TEST

Confidence belongs in
every pull request.

Airlock provides a run-submission API plus a local Playwright toolkit with request policies, browser-state checkpoints, and evidence utilities.

⌑01 / REQUEST POLICY

Apply request policies in the browser context.

Configure host, path, and method rules and substitute configured phantom tokens on intercepted browser requests. This prototype is not an OS-level egress firewall.

Explore the workflow →
◷02 / BROWSER STATE

Reuse browser state for test variations.

Capture browser storage and session state, then restore it into a new Playwright context. These are browser snapshots, not VM memory clones.

View the sample console →
◇03 / EXECUTION EVIDENCE

Create verifiable execution bundles.

AirlockQA can generate hash-linked ledger entries and signed bundles for verification with the configured key. This does not certify compliance.

See the response path →
BUILT FOR YOUR PIPELINE

One request.
A result your CI can use.

The cloud API exposes a run-submission route at POST /v1/runs. Cloud execution is still evolving; confirm the capabilities of your deployment before relying on run isolation or advanced diagnostics.

See the CI/CD setup →
GITHUB ACTIONSairlock.yml
jobs:
  browser-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npx airlock test --cloud
        env:
          AIRLOCK_API_KEY: <from CI secrets>
POST /v1/runsResult returned to CI ✓
